# Найденные расхождения и вопросы

## BUG-01 — разрешённые буквы G–Z отклоняются в токене

Приоритет: высокий. Основание: PDF и README приложения разрешают 32 символа A–Z0–9.

Воспроизведение: отправить POST /endpoint с правильным X-Api-Key, Content-Type application/x-www-form-urlencoded и телом `token=ABCDEFGHIJKLMNOPQRSTUVWXYZ012345&action=LOGIN`. Внешний /auth настроен отвечать HTTP 200.

Ожидается: JSON result=OK и запрос /auth с этим токеном.
Фактически: result=ERROR; причина содержит регулярное выражение `^[0-9A-F]{32}$`. Авторизация корректного по документации токена невозможна.

Автотест: EndpointTest.validToken, набор ABCDEFGHIJKLMNOPQRSTUVWXYZ012345. Ошибка подтверждена реальным запуском исходного JAR.

## QUESTION-01 — пробел перед названием действия

POST с новым корректным токеном и action=` LOGIN` возвращает OK.
Автотест invalidAction ожидает ERROR, исходя из точного перечня допустимых значений. Однако нормализация пробелов в задании не определена. Это спорное ожидание, не подтверждённый дефект. Вопрос заказчику: нужно ли принимать названия действий с пробелами по краям? До уточнения проверка намеренно остаётся видимой и падающей.

## Допущения

HTTP 200 внешнего сервиса считается успехом, проверенные 4xx/5xx — ошибками. Поведение на 201/204/3xx не заявляется. Доступ с неверным ключом должен завершаться HTTP 401 или 403. Сохранение сессии после сбоя ACTION, повторный LOGIN и LOGOUT неизвестного токена не закреплены контрактом.
